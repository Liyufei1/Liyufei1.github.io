Obsidian 的 AI 化

把 Obsidian 知识库与 AI 结合的技术方案与路线图

2026-09-04
阅读时长: 4 分钟

本文记录「如何把 Obsidian 知识库与 AI 结合」的几种技术方案，以及针对当前仓库的推荐路线。

一、现状盘点

当前仓库是一个「双身份」目录：

E:\Study\Blog\                  # Hugo 站点（git 仓库根）
  content\post\                 # ← Obsidian 仓库根（也是 Hugo 内容目录）
    AI\  Blog\  Cpp\  Godot\  Python\  Render\  UE\   # 按主题分类的笔记
    .obsidian\                  # Obsidian 配置 + 插件
    .agents\  .claude\          # AI agent 配置

已具备的 AI 相关基础：

  • Termy 插件：内置终端，可带着「当前笔记 / 选中文本 / vault 根目录」上下文启动 claude / codex / opencode / gemini 四套 CLI。
  • AGENTS.md：位于 Hugo 根目录，给 AI 看的博客开发指南。
  • .claude/settings.json、.agents/skills/：AI 工具配置。
  • 全程 git 版本控制，笔记已按主题分好类。

结论：目前只做到了「第 1 层——让 AI 作为 agent 直接读写知识库」。下面的方案补齐其余层次。

二、「AI 化」的四个层次

层次 能力 当前状态
① Agent 操作 AI 能读/写/搜仓库文件 ✅ 已通过 Termy + CLI 实现
② 结构认知 AI 理解库的结构、约定、规则 ⚠️ 部分（AGENTS.md 不全，vault 根无 CLAUDE.md）
③ 语义检索 AI 从全库检索相关片段再回答 ❌ 缺（只能塞上下文里的那几篇）
④ 图谱推理 跨多篇笔记做多跳推理 ❌ 缺（暂不需要）

三、方案 A：把 CLI Agent 模式「规整化」（零成本）

问题：AI 每次启动只知道「当前这篇笔记」，对全库结构没有统一认知——AGENTS.md 在 Hugo 根目录，vault 根目录 content/post/ 下没有 CLAUDE.md。

做法：在 content/post/（vault 根）新建 CLAUDE.md，写清：

  • 目录结构，以及每个分类（AI/Blog/Cpp/Godot/Python/Render/UE）是干什么的
  • 笔记规范：frontmatter 字段、draft 用法、图片路径约定（ImageBG/ImageTemp）、[[双向链接]] 约定
  • 哪些文件别动：.obsidian/、.agents/、.claude/

效果：任何 AI（Claude Code / Codex / Gemini）一进 vault 就「懂规矩」。这是所有后续方案的底座。

四、方案 B：语义检索 + 全库问答（RAG）——最缺的一层

现在 AI 只能看到「塞进上下文里的那几篇」。要做到「问整个知识库、AI 从全库检索相关片段来回答」，需要一层向量检索。

工具 形式 特点 适配度
Smart Connections Obsidian 插件 本地 embedding，自动算「相似笔记」+ 对全库聊天 ✅ 最省事，免费本地
Khoj 自托管服务 + 插件 开源「第二大脑」，可接本地/云端模型 想要更强可控性再上
AnythingLLM / Cherry Studio 独立 app 拖入目录建知识库，接任意模型 想要 UI、不写代码
自建（LanceDB / Chroma + Claude API） 写代码 完全可控，能定制检索 技术向，想深挖再走

判断：笔记含大量代码和术语（C++/Vulkan/Godot），语义检索价值最大（如「我写过哪些 Godot 动态类型的内容」能直接问出来）。先用 Smart Connections 零成本跑起来，不够再升级。

五、方案 C：用 MCP 把 Obsidian 变成标准数据源

2025-2026 年的「正统」路线。装一个 Obsidian MCP server（mcp-obsidian / obsidian-mcp-tools），然后：

  • Claude Code：claude mcp add 接上 → AI 能按需搜索、读写 vault，不用把所有笔记塞进上下文
  • Claude Desktop：也能接，直接在桌面 app 里问答知识库

与 A/B 的区别：A 是「给 AI 一份说明书」，B 是「加一个检索库」，C 是「给 AI 一把能实时读写的 API 钥匙」。Termy 已在做类似的事，但 MCP 更标准、工具粒度更细（按标签搜、按标题搜、列文件夹等）。

六、方案 D：知识图谱 / GraphRAG（进阶，暂缓）

把笔记间的 [[双向链接]]、标签、概念关系抽成图（Neo4j 或直接利用 Obsidian graph），做多跳推理——适合「跨多篇笔记推一个结论」。

对现状过早：才 27 篇、结构已很清晰，图检索收益不如先做 B。等库到几百篇、链接密度高了再上。

七、推荐路线图

  1. 立刻（今天）：方案 A——在 vault 根写 CLAUDE.md 固化结构约定；同时给 Claude Code 挂 Obsidian MCP（方案 C），让「读库」变成按需工具而非塞上下文。
  2. 本周：装 Smart Connections（方案 B），跑本地索引，感受「相似笔记 + 全库问答」。
  3. 以后：库变大、链接变密，再上 GraphRAG（方案 D）。

八、下一步行动清单

  • 在 content/post/ 写 CLAUDE.md
  • 调研 mcp-obsidian / obsidian-mcp-tools 接入步骤
  • 安装 Smart Connections，跑本地索引
  • （可选）评估 Khoj / 自建 RAG 是否需要
  • （远期）库规模上去后评估 GraphRAG
