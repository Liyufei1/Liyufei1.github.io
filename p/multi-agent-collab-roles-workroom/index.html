多 Agent 协作：角色设定与 WorkRoom 工作间方向

梳理多智能体协作的两大核心——给 Agent 设定角色、共享 WorkRoom 工作间，并盘点已开源实现的相关工程

概述

随着单个 LLM 的能力趋于成熟，2025 年下半年起，“多 Agent 协作"成了 AI 应用层的热门方向。这篇文章想讲清楚三件互相咬合的事：

  1. 多 Agent 协作 —— 为什么要让多个 Agent 一起干活，而不是一个 Agent 扛下所有；
  2. 给 Agent 设定角色 —— 怎么把一个"万能助手"拆成各司其职的"专家”；
  3. WorkRoom 工作间方向 —— 更前沿的一种做法：不再纠结"选哪个 Agent 框架"，而是让已有的多个 Agent（Claude Code、Codex、OpenCode、Cursor……）共享同一个工作间，一起协作。

文章最后会重点盘点已经开源、已经落地实现的相关工程，方便直接上手。

为什么要多 Agent 协作

单个 Agent（哪怕是能力最强的模型）在实际工程里有几个绕不过去的短板：

  1. 上下文有限：一个对话窗口装不下超大项目的全部信息，塞多了反而让模型"抓不住重点"；
  2. 职责混杂：既当产品经理、又当架构师、又写代码、又做测试，容易顾此失彼、前后矛盾；
  3. 幻觉会级联：一个环节出错的结论，会被当成"既定事实"继续往下推导，越错越远。

多 Agent 协作的核心思路，就是把一个大任务拆成多个职责清晰的小角色，让它们各管一段、互相校验。这和人类团队的分工协作是同一个逻辑。

带来的直接好处：

  • 每个 Agent 的上下文更小、更聚焦，表现更稳定；
  • 不同角色可以并行工作，缩短总耗时；
  • 关键环节可以用"另一个 Agent 来审查/质疑"，抑制幻觉级联。

给 Agent 设定角色

角色的本质

一句话概括：角色 = 一段系统提示词（人设 + 职责边界） + 工具集 + 权限。

所谓"设定角色"，本质上就是给模型一段专门的身份描述，约束它"你是谁、该做什么、不该做什么、能调用哪些工具"。区别只在于不同框架把这层抽象暴露成什么 API。

三种典型做法

1. 角色扮演式：CrewAI

CrewAI 用 role / goal / backstory 三个字段把角色拟人化，是上手最快、最直观的一种：

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="资深研究员",
    goal="调研多 Agent 框架的最新进展",
    backstory="你拥有十年技术调研经验，擅长从杂乱信息中提炼结论。",
)

writer = Agent(
    role="技术写手",
    goal="把调研结果写成易读的文章",
    backstory="你擅长把技术内容讲得通俗易懂。",
)

research_task = Task(description="调研主流多 Agent 框架的差异", agent=researcher)
write_task = Task(description="基于调研结果撰写一篇对比文章", agent=writer)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.sequential,   # 顺序执行：研究员 → 写手
)
crew.kickoff()

2. SOP 装配线式：MetaGPT

MetaGPT 把"角色"进一步固化成一条软件公司流水线：产品经理 → 架构师 → 工程师 → QA。它强制每个角色产出结构化中间产物（PRD、系统设计、API 规范），再交给下一个角色，用"文档"约束协作，从而抑制幻觉级联。

它的核心公式是 Code = SOP(Team)——重点不是"写代码"，而是用标准作业流程（SOP）组织一群 Agent。这套"角色 + 结构化产物 + 预算熔断"的设计思想，比它本身的代码更值得学。

3. 声明式 Subagent：Claude Code / OpenCode

OpenCode 也有类似的 ~/.config/opencode/agent/*.md 自定义 Agent 机制。声明式的好处是：角色可版本管理、可复用、可团队共享——它本身就是你博客仓库里 .claude/agents 和 .agents 目录正在做的事。

多 Agent 的编排模式

角色定了之后，还要决定这些角色之间怎么协作。主流框架提供了几种典型的"拓扑”：

编排模式 说明 代表实现
群聊 / 对话式 多个 Agent 在一个对话里轮流发言，由调度器决定谁说话 AutoGen 的 RoundRobinGroupChat、SelectorGroupChat
图编排 用"节点 + 条件边"显式定义流程，像状态机一样可控 LangGraph
主管 - 执行 一个 Manager/Supervisor 负责拆任务、分派、验收 CrewAI 的 Process.hierarchical、LangGraph Supervisor
流水线 / SOP 固定顺序，上一个角色的产出是下一个的输入 MetaGPT、CrewAI 的 Process.sequential
交接 Handoff Agent A 干到一半，把控制权"转交"给更合适的 Agent B AutoGen Swarm、OpenAI Agents SDK 的 handoff

选哪种模式，取决于任务是"流程固定"还是"需要动态探索"：流程固定用流水线/图编排最稳，开放探索用群聊/交接更灵活。

Agent WorkRoom 工作间方向

什么是 WorkRoom

上面讲的多 Agent 框架，大多是在一个程序进程里编排多个角色。而 “WorkRoom”（工作间 / 房间）是 2025 年末开始冒头的一种更务实的方向：

不再造一个新的 Agent 框架，而是给已有的、不同厂商的 CLI Agent（Claude Code、Codex CLI、OpenCode、Cursor、OpenClaw……）提供一个共享的工作空间，让它们像在一个聊天室里一样协作。

它的几个标志性特征：

  • 房间 / 线程：多个 Agent 处在同一个共享上下文里，能看到彼此的动作和产物；
  • @提及路由：用 @claude 审查 API、@codex 写测试 这种自然语言把任务派给具体 Agent；
  • 共享文件 / 浏览器：Agent 不止"聊天"，还共同读写同一批文件、同一个浏览器；
  • 审批与门禁：人对关键操作（改文件、执行命令）保留最终裁决权。

这个方向的洞察很朴素：不同 Agent 各有所长，与其逼一个 Agent 面面俱到，不如让一群现成的 Agent 同处一室、互相补位。

已开源实现的工程

OpenAgents Workspace —— “Slack for agents”

  • 一句话：面向 AI Agent 的协作操作系统，浏览器里开一个共享工作空间。
  • 核心能力：共享线程、共享文件、共享浏览器；用 @mention 把任务派给不同 Agent（例如 @claude 审查 API，@codex 写集成测试）。
  • 组成：Workspace（浏览器协作）+ Launcher（agn CLI，负责安装/管理 Agent）+ Network SDK（扩展层）。
  • 现状：Apache 2.0，约 3.3k stars，已支持 Claude Code、Codex CLI、OpenCode、Cursor、OpenClaw、Hermes 等。

OpenGrove —— 本地优先的 Agent 之家

  • 一句话：local-first 的工作空间，把多个 coding Agent"收编"到同一个屋檐下。
  • 核心能力：Rooms（私聊 / 群聊）+ @mention 路由到具体 Agent；本地记忆、产物、运行轨迹都存成你自己拥有的本地文件；文件改动 / 命令执行需显式审批。
  • 多内核：一套 UI 里切换 Codex、Claude Code、Hermes、OpenCode、Copilot、Kimi、Qwen Code 等 13+ 内核。
  • 本地优先：默认跑在 127.0.0.1，远程协作是可选项（经 Matrix/Tuwunel）。

AgentWork —— 自主编排器

  • 一句话：“You manage. Agents work 24/7."——面向自主任务编排。
  • 核心能力：Rooms 与 Meetings 概念，支持自主会议编排与任务生成；Node.js daemon + REST API + SQLite；支持 9 家厂商、80+ 模型；带 Git 自动化、Telegram/Slack/Discord 机器人、MCP Server、VS Code 插件。

Multi-Agent Workbench —— 结构化 Task Room

  • 一句话：浏览器里的结构化 “Task Room”，让多个 CLI Agent 并排干活。
  • 核心能力：一个房间 = 目标 + 成员 + 时间线 + 决策 + 审批 + 产物；Claude Code、Codex、通用 PTY CLI 在同一房间内按明确角色协作；角色卡片、带决策门禁的编排器、事件溯源（23 类事件）、git worktree 隔离。
  • 特点：本地优先，无账号、无云端、无遥测。

其他值得关注

  • Buzz（Block）：可自托管的人机协作工作空间，基于 Nostr 中继。
  • OCWS（OpenClaw Workspace Spec）：为"一人公司 / 多机器人协作"设计的轻量工作空间协议，用目录结构 + 通知文件来协调多个 Agent。

怎么选

  • 想在一个框架里快速搭一套多 Agent 流程 → 先试 CrewAI，角色概念直观、从 0 到 Demo 最快；
  • 流程固定、要求高可靠 / 合规（金融、医疗审批）→ LangGraph，图编排可控、可回放调试；
  • 想研究多 Agent 的"正确姿势”（SOP、结构化产物） → 读 MetaGPT 的源码与思想；
  • 已有多个 CLI Agent，想让它们"同处一室"协作 → 直接上 WorkRoom 类工程：本地优先选 OpenGrove / Multi-Agent Workbench，想浏览器协作选 OpenAgents Workspace。

小结

多 Agent 协作的三个层次，本质上是同一件事的三种切面：

  1. 角色解决"谁来干、干什么"；
  2. 编排模式解决"怎么配合"；
  3. WorkRoom 工作间解决"在哪儿一起干"。

而 WorkRoom 方向特别值得关注：它绕开了"再造一个框架"的军备竞赛，转而解决更实际的问题——把现成的、各有所长的 Agent 组织起来。对普通开发者来说，这可能比再学一个新框架更省力、也更快见效。
