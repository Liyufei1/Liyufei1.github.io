UE 引入第三方库的几种方式

梳理 UE5 中引入 C++ 第三方库的几种主流方式及其优缺点对比，帮助根据项目场景选择最合适的集成方案。

2026-07-01
阅读时长: 4 分钟

一、概述

  • 引擎版本：5.5.4
  • 编译链: MSVC\14.38.33130

在 Unreal Engine 的 C++ 开发中，引入第三方库是常见需求——无论是网络库、压缩库、数学库，还是 SDK 接入。UE 的构建系统（UnrealBuildTool, UBT）提供了多种集成路径，从简单粗暴的直接链接，到规范化的插件封装，各有适用场景。

本文将梳理 2种主流方式，并进行逐步流程说明

二、两种引入方式详解

2.1、UBT 外部模块（External Module）

这是引擎内部使用最广泛的模式。在 Source/ThirdParty/ 下为每个三方库创建独立的 .Build.cs，并声明 Type = ModuleType.External。

这是 UE 引擎源码中 PhysX、OpenGL、Vulkan、Oculus、Steam 等模块采用的方式——将三方库封装成与引擎模块一致的接口，上层代码无感引用。

  • 优点：
    • 目录结构规范；
    • 跨平台条件编译集中在一处；
    • 通过模块依赖管理，
    • 可被多个模块复用。
  • 缺点：
    • 需要额外维护一个 .Build.cs 文件；`
    • ModuleType.External` 模块无法包含 C++ 源码（仅能做链接和头文件暴露）。

using UnrealBuildTool;
using System.IO;

public class MyLib : ModuleRules
{
    public MyLib(ReadOnlyTargetRules Target) : base(Target)
    {
        Type = ModuleType.External;  // 关键：声明为外部模块

        string LibDir = ModuleDirectory;
		
		// 1.添加头文件路径
        PublicIncludePaths.Add("$(ModuleDir)/include");

        if (Target.Platform == UnrealTargetPlatform.Win64)
        {
	        // 2.添加静态链接库（可选）
            PublicAdditionalLibraries.Add(Path.Combine(LibDir, "lib", "Win64", "MyLib.lib"));
            
            // 3.添加动态链接库（可选）
            // RuntimeDependencies.Add(Path.Combine(ThirdPartyPath, "bin", "Win64", "Release", "boost_lib.dll"));
            
            // 4.动态链接库延迟加载（可选）
            // PublicDelayLoadDLLs.Add("boost_lib.dll");
        }
        else if (Target.Platform == UnrealTargetPlatform.Linux)
        {
            PublicAdditionalLibraries.Add(Path.Combine(LibDir, "lib", "Linux", "libMyLib.a"));
        }
        // Android / iOS ...
    }
}

2.2、 封装为 UE 插件（Plugin）

最规范、可复用性最高的做法。内部也是使用了UBT的外部模块（External Module）

  • 优点：

    • 独立分发：插件可跨项目复用，可直接放入引擎 Engine/Plugins/ 或项目 Plugins/ 目录
    • 市场分发：可发布到 UE Marketplace
    • 蓝图友好：可在插件中封装蓝图函数库，让非 C++ 开发者也能使用
    • 版本管理清晰：.uplugin 自带版本号

  • 缺点：

    • 前期搭建成本最高
    • 小项目可能"杀鸡用牛刀"
    • 引擎大版本升级时可能需要适配 .uplugin 格式

三、常见踩坑点

  1. CRT 链接方式不一致：Windows 上 UE 使用 /MD（动态链接 CRT），如果你的 .lib 是用 /MT 编译的，会报 LNK2038 或运行时崩溃。确保三方库的编译选项与 UE 匹配。

  2. Public vs Private 的选择：如果在公共头文件中 #include 了三方库的头文件，必须用 PublicIncludePaths 和 PublicAdditionalLibraries；如果只在 .cpp 中使用，用 Private* 版本可以减少依赖模块的重新编译。

  3. ModuleType.External 不参与源码编译：如果你需要包装三方库的初始化逻辑，需要在 External 模块之外再建一个 Runtime 模块来写胶水代码。

  4. 动态库的平台差异：Windows 需要 .dll + .lib（导入库）；Mac 用 .dylib；Linux 用 .so；Android 用 .so（放在 libs/arm64-v8a/ 等 ABI 目录下）。

  5. 许可证审查：集成前三方库前检查 License（MIT/BSD/Apache 2.0 通常安全；GPL/LGPL 需法务评估）。
