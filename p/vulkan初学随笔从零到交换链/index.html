Vulkan初学随笔：从零到交换链

从零到交换链的 Vulkan 初始化学习随笔——讲清实例、验证层、表面、物理设备、队列族、逻辑设备与交换链每个概念背后的为什么

2026-07-28
阅读时长: 22 分钟

本文是学习随笔而非教程搬运：主线是"从零到交换链"，讲清每个概念的为什么，而不只是怎么调 API。环境约定 Windows 10/11 + GLFW + C++17，平台差异点随文标注。文中所有初始化代码建议放进同一个程序里渐进演化（像 vulkan-tutorial.com 那样一个 main.cpp 从空文件开始逐步生长，按章拼接即得可运行程序），随笔的叙事顺序就是依赖顺序。术语约定：中文术语首次出现附英文原文，此后统一用中文；API 函数名、枚举与宏一律使用完整规范符号名。

第 0 章 为什么是 Vulkan：一份和驱动的明文合同

如果你写过或只是看过 OpenGL 的代码，一定熟悉那种体验：你说"画个三角形"，驱动在幕后替你决定状态怎么存、内存怎么分、同步怎么做。这套隐式魔法让入门变得容易，代价也有两个：同一份代码在不同驱动上行为可能不一致；多线程时代，驱动只能靠内部大锁去猜你的意图。

Vulkan 把这份默契换成了一份明文合同：内存你自己分配、同步你自己声明、状态你自己记录。代价是画一个三角形前要先写几百行初始化；回报是每一行"啰嗦"都在替驱动省掉一次隐式决策——你少猜一次，驱动就少猜一次。这是全文唯一的主线：显式控制不是繁琐，是把决策权从驱动手里拿回来。

本文走完"从零到交换链"这一段：窗口建好、显卡选好、拿到一沓可以轮流上屏的图像，并跑通第一帧的获取与呈现循环。渲染管线留给下一篇。

初始化全程共十二步。先给一张"到第一个三角形"的全景路线图：实线十二步是本文范围，只画不展开；虚线灰显部分属于下篇。后面每章开头都会标注自己所处的步骤（如"[7/12] 队列族"），迷路时回来对号入座：

第 1 章 实例：和驱动握手 [2–4/12]

解决什么问题。 程序要用 GPU，总得先和驱动建立联系。实例（instance）就是应用与 Vulkan 驱动之间的会话句柄、全局状态的入口：后续一切对象——物理设备、表面、逻辑设备——都从这里派生。注意方向性：是应用向驱动申请会话，应用本身并不拥有任何 GPU。

// 本章起点：程序尚无一物，从驱动的会话句柄开始
VkApplicationInfo appInfo{};
appInfo.sType = VK_STRUCTURE_TYPE_APPLICATION_INFO; // 结构体自报类型，Vulkan 靠它做校验与扩展
appInfo.pApplicationName = "Hello Vulkan";
appInfo.applicationVersion = VK_MAKE_VERSION(1, 0, 0);
appInfo.pEngineName = "No Engine";               // 引擎名，自填即可
appInfo.engineVersion = VK_MAKE_VERSION(1, 0, 0);
appInfo.apiVersion = VK_API_VERSION_1_3;         // 展开即 VK_MAKE_API_VERSION(0,1,3,0)

VkInstanceCreateInfo createInfo{};
createInfo.sType = VK_STRUCTURE_TYPE_INSTANCE_CREATE_INFO;
createInfo.pApplicationInfo = &appInfo;
// 还有两件事：启用哪些扩展（extension）、开哪些层（layer），见下文

VkApplicationInfo 是给驱动和工具看的元信息，不是能力开关：apiVersion 声明打算使用的最高版本，pEngineName 随便填也没人来查。版本号永远用宏拼装，别手写十六进制。apiVersion 也别虚高——老版本加载器（loader）会直接拒绝创建实例，新加载器虽已放宽，仍建议按实际用到的特性填写。

坑位提示：先查询、再启用。 扩展和层都必须先用 vkEnumerateInstanceExtensionProperties / vkEnumerateInstanceLayerProperties 枚举确认存在，再写进 createInfo。启用不存在的名字不会被静默忽略，而是返回 VK_ERROR_EXTENSION_NOT_PRESENT（扩展不存在）或 VK_ERROR_LAYER_NOT_PRESENT（层不存在），实例创建失败。“枚举 → 检查 → 启用"这个三拍子全文会出现五次以上，它是 Vulkan 安全感的一半来源。

最后一个伏笔：把调试回调的创建信息通过 pNext 挂进 VkInstanceCreateInfo，连实例创建/销毁本身出的错都能被捕获——细节下一章展开。

第 2 章 验证层：把崩溃变报错 [3–4/12]

解决什么问题。 出于性能考虑，Vulkan 规范把绝大多数误用定义为未定义行为（undefined behavior）：句柄用错、资源忘绑、同步没做——驱动不检查，直接崩给你看，而且往往崩得毫无线索。验证层（validation layer）就是救场用的注入式检查代码，可以理解为把编译器的警告和 sanitizer 搬进了运行时——只是检查对象从语言误用换成了 API 误用：参数校验、句柄生命周期、对象绑定丢失，新版本还内置同步验证（sync validation）。

代价与取舍。 天下没有免费的保护：每次 API 调用都要过一层拦截检查，帧率可能显著下降且时序改变；发布用户的机器上通常根本没装层。所以结论只有一条：验证层只进 Debug 构建。 官方层只有 VK_LAYER_KHRONOS_validation 一个；网上旧教程里的 LUNARG_standard_validation 是已废弃别名，别再用。

这里有个设计决策值得停下来想：Debug 构建查不到层怎么办？warn-and-continue 还是硬失败？我的选择是后者——开发环境坏了要尽早暴露，静默降级只会把痛苦推迟到更难查的地方。于是用条件编译分流：

bool checkValidationLayerSupport() {
    uint32_t count;
    vkEnumerateInstanceLayerProperties(&count, nullptr);            // 第一次：拿数量
    std::vector<VkLayerProperties> available(count);
    vkEnumerateInstanceLayerProperties(&count, available.data());   // 第二次：填内容

    cbInfo.sType = VK_STRUCTURE_TYPE_DEBUG_UTILS_MESSENGER_CREATE_INFO_EXT;
    cbInfo.messageSeverity = VK_DEBUG_UTILS_MESSAGE_SEVERITY_WARNING_BIT_EXT
                           | VK_DEBUG_UTILS_MESSAGE_SEVERITY_ERROR_BIT_EXT;
    cbInfo.messageType = VK_DEBUG_UTILS_MESSAGE_TYPE_GENERAL_BIT_EXT
                       | VK_DEBUG_UTILS_MESSAGE_TYPE_VALIDATION_BIT_EXT
                       | VK_DEBUG_UTILS_MESSAGE_TYPE_PERFORMANCE_BIT_EXT;
    cbInfo.pfnUserCallback = debugCallback;
    create(instance, &cbInfo, nullptr, &debugMessenger);

两处细节：其一，函数指针的异型转换 static_cast 编不过，必须 reinterpret_cast——很多人的第一块绊脚石就在这；其二，message type 枚举以所用 SDK 头文件为准，较新的头文件另有 VK_DEBUG_UTILS_MESSAGE_TYPE_DEVICE_ADDRESS_BINDING_BIT_EXT 一类的新位。想让实例创建期的错误也进回调，就把同一份 cbInfo 通过 pNext 挂进 VkInstanceCreateInfo；销毁时用同样动态取址拿到的 vkDestroyDebugUtilsMessengerEXT，且要在 vkDestroyInstance 之前。

坑位提示。 别在 Release 里请求验证层：用户机器没装层，vkCreateInstance 直接报错，程序当场起不来——上面的 #ifdef NDEBUG 分流正是为此。默认掩码只开 WARNING|ERROR 是为了输出清爽；想看 INFO 甚至 VERBOSE，往 cbInfo.messageSeverity 里再加一位即可——初学阶段值得开一阵子。

第 3 章 窗口与表面：把画面接到屏幕 [1、5/12]

解决什么问题。 Vulkan 本身没有"窗口"的概念——它只管 GPU 计算，窗口系统是各平台的私事。于是分层解决：VK_KHR_surface 提供抽象接口，VK_KHR_win32_surface（Linux 上是 xcb/wayland 变体）提供平台实现，而跨平台窗口创建干脆交给 GLFW 这类库。我们要做的只是在两者之间架桥：表面（surface）。

三步依次发生。第一步，创建一个"不属于 OpenGL"的窗口——没有 GLFW_CLIENT_API 这行 hint，GLFW 会按默认值创建 OpenGL 上下文占住原生窗口，等后面建表面时报出 VK_ERROR_NATIVE_WINDOW_IN_USE_KHR（原生窗口已被占用），错误离案发现场隔着一整章；同理，此后也不要调用 glfwMakeContextCurrent，那是 OpenGL 的概念，Vulkan 没有"当前上下文"一说。第二步，问 GLFW 要实例扩展清单——平台需要哪些扩展它最清楚。第三步，建桥：

Vulkan 怎么建模。 记住一件事：表面是实例级对象，挂在实例下面而不是任何 GPU 下面。为什么选卡之前就要先把表面建好？因为"这块卡能不能往这个窗口呈现"是设备×表面的组合属性——下一章面试显卡时要拿它当考题。伏笔至此，下章兑现。

坑位提示：错误延迟爆炸。 本章最大的坑其实是第 1 章埋下的：如果当初忘了合入 GLFW 要求的实例扩展，一切看似正常，直到创建表面甚至更后面的交换链才爆炸，报错离根因极远。遇到莫名其妙的 WSI 报错，第一反应是回头数一遍实例扩展清单。

第 4 章 物理设备：面试你的显卡 [6/12]

Vulkan 怎么建模。 物理设备（physical device）是驱动递给你的"这块 GPU 能力说明书”：只读句柄，不能由你创建，只能枚举。（顺带纠偏：别把 vkFreeMemory 错用来释放枚举结果这类宿主端数组——那是释放显存对象 VkDeviceMemory 的接口；C++ 里交给 std::vector，RAII 从根上免掉手工释放。）

面试清单。 存在合法设备 ≠ 默认第 0 个合适——双显卡笔记本上第 0 个常是核显。逐项过堂：

  • 支持图形队列族（第 5 章细讲）；
  • 能向我们的表面呈现；
  • 支持 VK_KHR_swapchain 设备扩展；
  • 该扩展之下格式与呈现模式列表非空（第 7 章细讲）；
  • 打分排序：离散显卡加分，limits.maxImageDimension2D 之类可作粗糙的能力参考。

第 5 章 队列族：GPU 的多条流水线 [7/12]

解决什么问题。 你提交给 GPU 的一切工作——绘制、计算、拷贝——最终都排进队列（queue）执行。Vulkan 不给一条万能队列，而是按能力把队列分成若干队列族（queue family）：同族共享能力位，如 GRAPHICS、COMPUTE、TRANSFER（个别还有 SPARSE）。驱动借此把不同性质的活调度到硬件的不同引擎上。

图形 ≠ 呈现（graphics vs present）。 这是本章最重要的认知纠偏：“能画"和"能把结果送上屏幕"是两种能力。打个比方：会画画的员工，不一定会把画挂到你这面墙上——绘制能力长在 GPU 身上，呈现能力却要对着具体的表面逐族确认。呈现是针对特定表面的属性，要用三元组（物理设备 × 表面 × 族索引）查询。多数显卡上图形族恰好也能承担呈现，两个族索引经常相同，但不可假设。顺带认识 transfer 专用族（只有 TRANSFER 位）：它能与图形队列并行做上传拷贝，是日后异步资源上传优化的入口，入门阶段知道它"为什么存在"即可。

// 承接第3章 surface：对每张通过初筛的卡执行本函数
// 呈现支持的完整签名：三元组缺一不可
VkBool32 supported = VK_FALSE;
vkGetPhysicalDeviceSurfaceSupportKHR(physicalDevice, familyIndex, surface, &supported);

struct QueueFamilyIndices {
    std::optional<uint32_t> graphicsFamily;   // 具备图形能力的族索引
    std::optional<uint32_t> presentFamily;    // 可向表面呈现的族索引
    bool isComplete() const {
        return graphicsFamily.has_value() && presentFamily.has_value();
    }
};

QueueFamilyIndices findQueueFamilies(VkPhysicalDevice device, VkSurfaceKHR surface) {
    QueueFamilyIndices indices;
    uint32_t count = 0;
    vkGetPhysicalDeviceQueueFamilyProperties(device, &count, nullptr);
    std::vector<VkQueueFamilyProperties> families(count);
    vkGetPhysicalDeviceQueueFamilyProperties(device, &count, families.data());

    for (uint32_t i = 0; i < count; ++i) {
        if (families[i].queueFlags & VK_QUEUE_GRAPHICS_BIT)
            indices.graphicsFamily = i;
        VkBool32 present = VK_FALSE;
        vkGetPhysicalDeviceSurfaceSupportKHR(device, i, surface, &present);
        if (present) indices.presentFamily = i;
        if (indices.isComplete()) break;
    }
    return indices;
}

第 6 章 逻辑设备：签一份能力合同 [8–9/12]

解决什么问题。 物理设备的说明书太全，你的程序只用其中一角。逻辑设备（logical device，类型名就叫 VkDevice）是对物理设备的程序视角切片：你声明要用哪些队列、哪些特性、哪些扩展，驱动据此分配资源。这份"先声明、后使用"的合同，是显式哲学最典型的一次亮相。

合同有三个必答条款。

其一，队列。 要哪个族的几条队列？注意 VkDeviceQueueCreateInfo 必须携带 queuePriorities 浮点数组（0.0~1.0，同族多队列时的调度权重）——哪怕只要一条队列，也得传长度为 1 的数组。没有默认值的字段就不该有默认值，很 Vulkan。另外同一族只能出现一次，重复放两个 createInfo 会被验证层点名。

其二，设备扩展。 明明实例级写过一遍，设备级为什么还要重申 VK_KHR_swapchain？因为作用域不同。打个比方：**实例扩展像驾照，证明你能开车上路——找到系统里的 GPU 和窗口系统；设备扩展像某辆车的改装许可——允许你动这台具体机器的特定功能。两本证各管各的路。**加载器依据两层声明决定暴露哪些入口点——不声明交换链扩展，vkAcquireNextImageKHR、vkQueuePresentKHR 这些函数可能根本取不到。所以创建前先用 vkEnumerateDeviceExtensionProperties 核验一遍（又是先查询再启用），防一手 VK_ERROR_EXTENSION_NOT_PRESENT（声明了不存在的扩展）。

其三，特性。 VkPhysicalDeviceFeatures 是一整版布尔开关（samplerAnisotropy、tessellationShader……），需要什么开什么，其余留 false——开关开得越多，驱动预留的资源越多。

第 7 章 交换链：三要素谈判 [10–12/12]

解决什么问题。 屏幕那头是显示引擎，永不停歇地扫描显存里的图像往外送；你这头是不停生成新一帧的程序。双方速度不一致、节奏不合拍，就需要一组"轮流上岗"的图像来仲裁——这就是交换链（swapchain）：一沓由呈现引擎管理的可呈现图像，你画一张交出去，再领一张回来画。它不是 Vulkan 核心的东西而是 WSI 扩展提供的，前面一整串铺垫正是为了拿到签约资格。

struct SwapchainSupportDetails {
    VkSurfaceCapabilitiesKHR capabilities;       // 能力上限：张数范围、尺寸范围、变换等
    std::vector<VkSurfaceFormatKHR> formats;     // 支持的"格式×色彩空间"菜单
    std::vector<VkPresentModeKHR> presentModes;  // 支持的呈现模式菜单
};

SwapchainSupportDetails querySwapchainSupport(VkPhysicalDevice device, VkSurfaceKHR surface) {
    SwapchainSupportDetails d;
    vkGetPhysicalDeviceSurfaceCapabilitiesKHR(device, surface, &d.capabilities);
    uint32_t count;
    vkGetPhysicalDeviceSurfaceFormatsKHR(device, surface, &count, nullptr);
    d.formats.resize(count);
    vkGetPhysicalDeviceSurfaceFormatsKHR(device, surface, &count, d.formats.data());
    vkGetPhysicalDeviceSurfacePresentModesKHR(device, surface, &count, nullptr);
    d.presentModes.resize(count);
    vkGetPhysicalDeviceSurfacePresentModesKHR(device, surface, &count, d.presentModes.data());
    return d;
}

VkSurfaceFormatKHR chooseFormat(const std::vector<VkSurfaceFormatKHR>& formats) {
    for (const auto& f : formats)
        if (f.format == VK_FORMAT_B8G8R8A8_SRGB &&
            f.colorSpace == VK_COLOR_SPACE_SRGB_NONLINEAR_KHR) return f;
    if (formats[0].format == VK_FORMAT_UNDEFINED)      // 老驱动边角案例：菜单只给"随你挑"
        return { VK_FORMAT_B8G8R8A8_SRGB, formats[0].colorSpace };
    return formats[0];                           // 没得挑就认第一个
}

VkPresentModeKHR choosePresentMode(const std::vector<VkPresentModeKHR>& modes) {
    for (auto m : modes)
        if (m == VK_PRESENT_MODE_MAILBOX_KHR) return m;   // 示例取低延迟；在意续航/风扇就删掉本行退回 FIFO——谈判的意义所在
    return VK_PRESENT_MODE_FIFO_KHR;             // 保底：规范保证唯一必支持
}

要素一：格式（format）。 每张图的像素布局与色彩空间，优先 VK_FORMAT_B8G8R8A8_SRGB 或 VK_FORMAT_R8G8B8A8_SRGB 配 VK_COLOR_SPACE_SRGB_NONLINEAR_KHR——SRGB 格式让硬件写入时自动做伽马校正，人眼看着才"正常"，原理一句话带过、值得另立一文。列表若给出 VK_FORMAT_UNDEFINED，意为"随你挑"，那就回到首选。

要素二：呈现模式（present mode）。 决定图像何时被送去显示，四种模式一张表看懂：

枚举 语义 直观感受
VK_PRESENT_MODE_FIFO_KHR 垂直同步队列排队，错过节拍等下一拍 经典 vsync；规范保证唯一必支持
VK_PRESENT_MODE_FIFO_RELAXED_KHR 大体 FIFO，但晚到了就立即呈现 低负载延迟更低，代价是可能撕裂
VK_PRESENT_MODE_MAILBOX_KHR 单槽队列，新帧替换旧帧 近似三重缓冲，低延迟可丢帧；功耗发热代价
VK_PRESENT_MODE_IMMEDIATE_KHR 立即呈现 延迟最低，允许撕裂

选型提醒：“MAILBOX 一定最好"是想当然——笔记本上徒增功耗与发热；FIFO 是唯一保底，菜单里挑不到更好的就用它。

要素三：范围（extent）。 图像的像素尺寸。capabilities.currentExtent.width == UINT32_MAX 是特殊值，意为"尺寸由你定”——但即便如此也必须夹进 [minImageExtent, maxImageExtent]。尺寸基准要用像素而不是屏幕坐标：glfwGetFramebufferSize 返回像素，glfwGetWindowSize 返回屏幕坐标，HiDPI 下两者不同，永远取前者再 clamp。

关于共享方式多说一句：本文固定 VK_SHARING_MODE_EXCLUSIVE。原因有二：其一，VK_SHARING_MODE_CONCURRENT 要求 pQueueFamilyIndices 列出至少两个不同的族索引才合法——图形族与呈现族同族的常见情形下它根本用不上；其二，即便异族可用，也要多传一份族索引数组。单族独占没有额外成本，是最省心的合法选项。另外注意，这些图像的所有权在呈现引擎手里：用可以随便用，销毁却轮不到你——回收它们的方式只有一个，销毁整个交换链。

图像视图的概念一句话：图像只是裸数据，渲染前还要告诉管线"怎么解读这段数据"——格式、层级、维度。image 是数据，view 是视角。

至此 N 张图在手。它们如何轮流上岗？窗口拉伸后尺寸失效怎么办？这正是下一章的内容，也是 VK_ERROR_OUT_OF_DATE_KHR（交换链已过期）与 VK_SUBOPTIMAL_KHR（次优、仍可用）两个著名错误码登场的舞台。

第 8 章 第一帧：获取-提交-呈现循环 [12/12]

Vulkan 怎么建模。 主循环三拍子：vkAcquireNextImageKHR 从交换链领取一张可用图（必要时等显示引擎回收）；把这一帧画进去后 vkQueueSubmit 提交；vkQueuePresentKHR 把图交还给显示引擎上屏。三拍子横跨 GPU 内部与 CPU↔GPU 两种边界，各配一对信号量（semaphore）：

信号量 发出方（signal） 等待方（wait）
imageAvailable vkAcquireNextImageKHR（图真的可用了） vkQueueSubmit（等到图再开始往里画）
renderFinished vkQueueSubmit（画完了） vkQueuePresentKHR（等到画完再上屏）

信号量管 GPU 内部的先后顺序，二值、一次性：signal 一次、wait 一次，然后回收复用。但还有第三种节奏它管不了：CPU 录制命令缓冲（command buffer）的速度远快于 GPU 执行，若无约束，CPU 会在命令缓冲还在 GPU 上执行时就覆写它——这是未定义行为。管 CPU↔GPU 完成通知的是另一种原语：栅栏（fence），CPU 可以用它阻塞等待 GPU 真正完成。配合顺序是"等旧帧 → 领新图 → 确认这一帧真的要画了，才复位栅栏"。复位时机是个隐蔽陷阱：若先复位后领取，而领取恰逢交换链过期失败，本帧便不再提交，被复位的栅栏永远等不到下一次 signal——程序从第二轮起彻底冻结。谁先谁后必须写明，这是显式哲学的又一次亮相；创建栅栏时还要记得加 SIGNALED 位，否则第一帧之前没有"上一帧"，首轮等待就会永久阻塞：

// 让图像真正变色是下一篇渲染管线的事
void recordCommandBuffer(VkCommandBuffer cmd, uint32_t /*imageIndex*/) {
    VkCommandBufferBeginInfo beginInfo{};
    beginInfo.sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_BEGIN_INFO;
    vkBeginCommandBuffer(cmd, &beginInfo);
    vkEndCommandBuffer(cmd);
}

// 承接第6章 device/graphicsQueue/presentQueue、第7章 swapchain 与本章同步对象、命令缓冲
void drawFrame() {
    vkWaitForFences(device, 1, &inFlightFence, VK_TRUE, UINT64_MAX);  // 等 GPU 干完上一帧

    uint32_t imageIndex;
    VkResult result = vkAcquireNextImageKHR(
        device, swapchain, UINT64_MAX, imageAvailableSemaphore, VK_NULL_HANDLE, &imageIndex);

    if (result == VK_ERROR_OUT_OF_DATE_KHR) {      // 图没领到：当场重建，重来
        recreateSwapchain();
        return;                                // ★ 栅栏未复位仍为已signal态，下轮等待照常放行
    }
    // VK_SUBOPTIMAL_KHR：图到手了，本帧照常渲染，脏标记留给循环统一处理
    vkResetFences(device, 1, &inFlightFence);      // ★ 确认领到图才复位：此路径必然走到提交

    recordCommandBuffer(commandBuffer, imageIndex); // 真正的绘制指令属于下一篇管线

    VkPipelineStageFlags waitStage = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
    VkSubmitInfo si{};
    si.sType = VK_STRUCTURE_TYPE_SUBMIT_INFO;
    si.waitSemaphoreCount = 1;
    si.pWaitSemaphores   = &imageAvailableSemaphore;   // 等"图可用"
    si.pWaitDstStageMask = &waitStage;
    si.commandBufferCount = 1;
    si.pCommandBuffers   = &commandBuffer;
    si.signalSemaphoreCount = 1;
    si.pSignalSemaphores = &renderFinishedSemaphore;   // 发出"我画完了"
    vkQueueSubmit(graphicsQueue, 1, &si, inFlightFence);

    VkPresentInfoKHR pi{};
    pi.sType = VK_STRUCTURE_TYPE_PRESENT_INFO_KHR;
    pi.waitSemaphoreCount = 1;
    pi.pWaitSemaphores = &renderFinishedSemaphore;     // 等"画完了"
    pi.swapchainCount  = 1;
    pi.pSwapchains     = &swapchain;
    pi.pImageIndices   = &imageIndex;
    result = vkQueuePresentKHR(presentQueue, &pi);

    if (result == VK_ERROR_OUT_OF_DATE_KHR || result == VK_SUBOPTIMAL_KHR)
        frameResized = true;                           // 只置脏标记，下一轮循环开头重建
}

顺带一句提交信息里的 pWaitDstStageMask：本文固定 VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT，直觉是"等到可以开始写颜色的时机"再放行图像信号量（信号量正是在这个阶段点被消费，随手填 TOP_OF_PIPE 既白等又语义不配）——这个掩码不能随意填，深究留给续篇同步篇。

注意 VK_ERROR_OUT_OF_DATE_KHR 与 VK_SUBOPTIMAL_KHR 在获取与呈现两个调用点语义不同：vkAcquireNextImageKHR 返回前者，意味着图根本没领到，必须当场重建重领；vkQueuePresentKHR 返回其中之一时，则不必纠结这一帧是否已经上屏——置脏标记，下一轮循环开头统一重建。只在其中一处处理、或干脆忽略返回值，症状都是窗口一拉伸就黑屏甚至崩溃。

边界声明：本文循环一次只有一帧在飞。多帧并发（frames-in-flight）节流、栅栏数组与信号量的安全复用策略都留作续篇——届时只需把单个栅栏扩成数组，循环骨架不变。

重建触发源除了这两个返回码，还有窗口事件本身——用 glfwSetFramebufferSizeCallback 注册回调置个脏标记就够了，不要在回调里直接重建（回调触发时机可能在主循环中途）。重建时最小化窗口要特判：宽高为 0 就挂起等事件，否则得到的范围不合法。

// 承接本章 drawFrame 的重建触发：整链逆序拆除再重建
void recreateSwapchain() {
    int w = 0, h = 0;
    glfwGetFramebufferSize(window, &w, &h);
    while (w == 0 || h == 0) {                 // 最小化：挂起直到窗口恢复
        glfwWaitEvents();
        glfwGetFramebufferSize(window, &w, &h);
    }
    vkDeviceWaitIdle(device);                  // 等 GPU 把手头的活干完
    cleanupSwapchain();                        // views → swapchain，逆序拆除
    createSwapchain();
    createImageViews();
    // createFramebuffers()：下一篇引入帧缓冲后，重建链条同样要带上它
}

重建范围是一条完整链条：交换链 → 图像视图 → 帧缓冲（framebuffer）一整条，漏掉中间任何一层都会拿到悬空引用（帧缓冲属下一篇内容，届时记得把它纳入同一条链）。oldSwapchain 参数可以让新旧链平滑交接，入门阶段整体销毁重建完全够用。另外栅栏和信号量不在重建之列——它们的生命周期与交换链无关。

坑位提示。 信号量配对错乱（获取阶段发出的信号量没人等待、复用了还没等完的二值信号量）、或者无栅栏保护就重录执行中的命令缓冲——这些验证层都能抓到，报错里会指认失约的是哪一对。学会读它的指认，比背规则有用得多。

第 9 章 小结与下一步

回头看，十二步初始化其实是在连续回答驱动的四个问题：你是谁（实例）；画在哪（表面）；用哪块卡、怎么用（物理设备 → 队列族 → 逻辑设备）；图怎么轮转（交换链 → 图像视图 → 帧缓冲）。每一步的啰嗦都是在替驱动省掉一次隐式决策——把决策权拿回手里的感觉，就是 Vulkan 的入门体验。

依赖链一句话串起：实例 → 表面 → 物理设备 → 队列族 → 逻辑设备 → 交换链 → 图像视图 → 帧缓冲 → 主循环。顺序不能换，因为后一步的参数就是前一步的产物。

下一篇让图像真正变色：图形管线（graphics pipeline）、渲染通道（render pass）、描述符（descriptor），以及多帧并发与同步原语全家桶。

实验收尾的清理顺序照录一行：vkDestroySwapchainKHR（连同图像视图与帧缓冲）→ vkDestroyDevice → vkDestroySurfaceKHR（或先 glfwDestroyWindow）→ vkDestroyInstance——后建先拆；表面与调试回调都挂在实例之下，必须赶在 vkDestroyInstance 之前销毁（回调部分第 2 章已讲），实验收尾才不会崩。
